# 第七章学习复盘笔记

> 这份笔记不是照抄教材，而是根据我自己的提问、卡点和理解过程整理出来的。后续继续学习第七章时，可以不断往这里追加。

## 1. 从第一章手写 Agent 回看 Agent 的本质

第一章里的 Agent 并不是一个神秘的东西，它本质上是一段 Python 控制流程。

最朴素的 Agent 可以理解成：

```text
Agent = 大模型 + 工具 + 一套循环流程
```

第一章的基本流程是：

```text
准备系统提示词
↓
把用户问题和提示词一起发给大模型
↓
大模型输出 Thought / Action / Action Input / Final Answer
↓
Python 程序解析大模型输出
↓
如果是 Action，就调用对应工具
↓
把工具结果追加进上下文
↓
再次把完整上下文发给大模型
↓
直到识别到 Final Answer，结束任务
```

这里最重要的一点是：大模型本身不会持续运行，也不会真的自己记住上一轮发生了什么。每次调用大模型时，它只知道这次请求里传进去的内容。

所以所谓“上下文”，其实是 Python 程序帮大模型维护的一段越来越长的文本或消息列表。

也就是说：

```text
大模型负责根据上下文生成下一步文本。
Python 程序负责判断文本、调用工具、维护上下文、决定是否继续循环。
```

## 2. 为什么需要框架

手写 Agent 可以帮助理解原理，但功能一多，代码会开始重复和混乱。

常见重复点包括：

- 每个 Agent 都要重复写调用大模型的代码。
- 每个 Agent 都要自己维护上下文和历史消息。
- 每个工具都要自己规定输入、输出和错误处理。
- ReAct、Reflection、Plan-and-Solve 等范式会重复写类似控制流程。
- 换 OpenAI、DeepSeek、通义、本地模型时，配置容易散落在各处。

所以框架的作用不是“显得高级”，而是把容易重复、容易出错的部分抽象成统一组件。

HelloAgents 大致把这些东西拆成：

```text
HelloAgentsLLM   统一调用大模型
Agent            智能体基类
SimpleAgent      简单对话智能体
ReActAgent       推理 + 行动智能体
ReflectionAgent  反思优化智能体
ToolRegistry     工具注册表
Message          统一消息格式
Config           配置管理
```

可以理解成：

```text
上层 Agent 不直接关心模型厂商、工具细节、消息结构。
框架把这些部分整理好，让 Agent 更专注于“如何完成任务”。
```

## 3. 第四章的 HelloAgentsLLM 是什么

第四章先实现了一个简单版的大模型客户端 `HelloAgentsLLM`。

它的作用是：

```text
封装底层大模型 API 调用，让 Agent 不直接依赖 OpenAI SDK。
```

第四章的结构大致是：

```python
class HelloAgentsLLM:
    def __init__(self, model=None, apiKey=None, baseUrl=None, timeout=None):
        self.model = model or os.getenv("LLM_MODEL_ID")
        apiKey = apiKey or os.getenv("LLM_API_KEY")
        baseUrl = baseUrl or os.getenv("LLM_BASE_URL")
        self.client = OpenAI(api_key=apiKey, base_url=baseUrl, timeout=timeout)

    def think(self, messages, temperature=0):
        response = self.client.chat.completions.create(...)
        return response_text
```

这里的 `OpenAI` 不是 Agent，也不是大模型本身，而是 OpenAI Python SDK 提供的客户端类。

可以把它理解成：

```text
OpenAI SDK 客户端 = 负责向模型服务发送 HTTP 请求的工具
```

虽然它叫 `OpenAI`，但不一定只能调用 OpenAI 官方模型。很多模型服务商都兼容 OpenAI 接口格式，例如 DeepSeek、通义、Kimi、Ollama、vLLM 等。

所以调用链可以理解为：

```text
Agent
↓
HelloAgentsLLM
↓
OpenAI SDK 客户端
↓
DeepSeek / OpenAI / 其他兼容服务
```

这层封装的价值是：Agent 只需要调用 `llm.think(messages)`，不用关心底层请求细节。

## 4. 第七章对 HelloAgentsLLM 做了什么升级

第七章是在第四章简单客户端的基础上继续升级。

主要升级点是：

- 支持多个模型提供商。
- 支持自动检测 provider。
- 支持本地模型服务，例如 Ollama、vLLM。
- 提供统一的 `invoke()`、`think()`、`stream_invoke()` 调用方法。

第七章里的初始化参数大致是：

```python
def __init__(
    self,
    model: Optional[str] = None,
    api_key: Optional[str] = None,
    base_url: Optional[str] = None,
    provider: Optional[str] = "auto",
    **kwargs
):
```

其中 `Optional[str]` 表示这个参数可以是字符串，也可以是 `None`。

例如：

```python
model: Optional[str] = None
```

意思是：

```text
model 可以传字符串，比如 "deepseek-chat"；
也可以不传，不传时就是 None。
```

不传时，程序通常会去 `.env` 或默认配置里找。

## 5. provider 到底是什么

`provider` 可以理解成“模型服务商”或“模型来源”的标签。

例如：

```text
openai      OpenAI 官方
deepseek    DeepSeek
qwen        通义千问 / DashScope
modelscope  ModelScope
kimi        Moonshot / Kimi
zhipu       智谱
ollama      本地 Ollama
vllm        本地 vLLM 服务
local       其他本地服务
```

它不只是一个普通名字，而是一个配置选择开关。

因为不同服务商需要不同的默认配置：

```text
DeepSeek:
api_key 可能来自 DEEPSEEK_API_KEY 或 LLM_API_KEY
base_url 默认 https://api.deepseek.com
model 默认 deepseek-chat

OpenAI:
api_key 可能来自 OPENAI_API_KEY 或 LLM_API_KEY
base_url 默认 https://api.openai.com/v1
model 默认 gpt-3.5-turbo

Ollama:
api_key 可以是 ollama
base_url 默认 http://localhost:11434/v1
model 默认 llama3.2
```

所以：

```python
HelloAgentsLLM(provider="deepseek")
```

意思是告诉框架：

```text
请按 DeepSeek 的规则去解析 key、url 和默认模型。
```

注意：

```text
provider 这个参数名是代码作者起的，理论上可以改，但全项目都要跟着改。
provider 的值如 "deepseek"、"openai" 是框架约定好的，不能随便乱写。
```

## 6. provider="deepseek" 时源码里发生了什么

当代码写成：

```python
llm = HelloAgentsLLM(provider="deepseek")
```

执行顺序大致是：

```text
1. 进入 HelloAgentsLLM.__init__()
2. 读取 model：优先用传入参数，其次用 LLM_MODEL_ID
3. 因为手动传入 provider="deepseek"，所以不会走自动检测
4. 调用 _resolve_credentials()
5. 进入 deepseek 分支
6. 解析 api_key 和 base_url
7. 如果没有模型名，使用默认模型 deepseek-chat
8. 创建 OpenAI SDK 客户端
```

DeepSeek 分支的核心逻辑是：

```python
resolved_api_key = api_key or os.getenv("DEEPSEEK_API_KEY") or os.getenv("LLM_API_KEY")
resolved_base_url = base_url or os.getenv("LLM_BASE_URL") or "https://api.deepseek.com"
```

意思是：

```text
api_key 优先级：
手动传入 api_key
↓
DEEPSEEK_API_KEY
↓
LLM_API_KEY

base_url 优先级：
手动传入 base_url
↓
LLM_BASE_URL
↓
https://api.deepseek.com
```

真正调用模型时，会执行：

```python
self._client.chat.completions.create(
    model=self.model,
    messages=messages,
    ...
)
```

虽然这里用的是 OpenAI SDK，但请求实际会发到 `base_url` 指向的 DeepSeek 服务。

## 7. 自动检测 provider 的坑

只有不传 provider 时，才会自动检测：

```python
llm = HelloAgentsLLM()
```

源码中自动检测的顺序大致是：

```text
1. 如果有 OPENAI_API_KEY，返回 openai
2. 如果有 DEEPSEEK_API_KEY，返回 deepseek
3. 如果有 DASHSCOPE_API_KEY，返回 qwen
4. 如果有 MODELSCOPE_API_KEY，返回 modelscope
5. 再根据 LLM_API_KEY 格式判断
6. 再根据 LLM_BASE_URL 判断
7. 都判断不出来，返回 auto
```

我在 Windows 上遇到的问题是：

```text
.env 里配置的是 DeepSeek 的 LLM_API_KEY，
但系统环境变量里已经存在一个旧的 OPENAI_API_KEY。
```

因为自动检测优先检查 `OPENAI_API_KEY`，所以框架误判成了 `openai`，并拿旧 key 去请求，导致 401。

解决方式：

```python
llm = HelloAgentsLLM(provider="deepseek")
```

这样可以绕开自动检测，强制走 DeepSeek 分支。

## 8. 本地模型调用：Ollama 和 vLLM 是否必须装

第七章提到了本地模型调用，主要是为了说明：除了调用云端 API，也可以把模型部署在本地。

本地部署的价值主要有：

- 隐私：数据不发给外部服务商。
- 成本：不再按 API token 计费，但要承担硬件、电费和维护成本。
- 可控性：可以自己选择模型、部署方式、上下文长度和日志策略。

但本地部署不是“完全没有成本”，而是成本结构变化了。

可以类比为：

```text
调用 API = 打车，每次付钱，但不用维护车。
本地部署 = 买车，不按每次出行付费，但要买车、加油、保养。
```

对当前学习第七章来说，不需要安装 Ollama 或 vLLM。

当前最稳学习配置是：

```text
使用 DeepSeek API 跑通 HelloAgentsLLM
↓
理解 Agent 如何调用 LLM
↓
理解 SimpleAgent / ReActAgent / ReflectionAgent
↓
理解 ToolRegistry 和工具调用
↓
以后遇到隐私、成本、高并发问题，再学习本地模型部署
```

## 9. BaseModel 是什么

`BaseModel` 通常来自 Pydantic：

```python
from pydantic import BaseModel
```

它可以理解成：

```text
一个带自动校验能力的数据类基类。
```

普通 Python 类只是装数据，不会主动检查类型。

而继承 `BaseModel` 后，可以定义稳定的数据结构：

```python
class Message(BaseModel):
    role: str
    content: str
```

这表示：

```text
Message 必须有 role 和 content 两个字段；
它们都应该是字符串。
```

在 Agent 框架里，消息格式非常重要，因为大模型 API 需要类似这样的结构：

```python
[
    {"role": "system", "content": "你是一个助手"},
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好，有什么可以帮你？"}
]
```

使用 `BaseModel` 定义 `Message` 的好处是：

- 保证消息结构统一。
- 自动检查字段类型。
- 方便转成 dict 或 json。
- 减少由于字段乱写导致的错误。

一句话总结：

```text
BaseModel 用来定义可靠的数据结构；在 Agent 框架中，它帮助 Message、Config、Tool 参数等对象保持格式稳定。
```

## 11. SimpleAgent 与 MySimpleAgent 的复盘

### 我的原始理解

学完第七章后，我从构建 `SimpleAgent` 开始复盘：框架自带的 `SimpleAgent` 只支持普通对话，不支持工具调用。在我们重写的 `MySimpleAgent` 中，引入了工具注册表，允许智能体调用工具。

当智能体对话时，它会先判断当前是否允许工具调用。如果不允许，就走普通对话流程；如果允许，就走工具调用流程。工具调用流程本质上也是一个循环：模型判断是否需要继续调用工具，如果不需要调用更多工具，或者达到最大循环次数，就停止并输出结果。

### 校准后的理解

这个理解主干是对的，但需要补充几个细节。

框架原生的 `SimpleAgent` 是一个纯对话 Agent，它的主要流程是：

```text
构建 messages
↓
加入 system_prompt
↓
加入历史消息 self._history
↓
加入当前用户输入
↓
调用 llm.invoke()
↓
把用户输入和模型回答保存进历史记录
↓
返回回答
```

也就是说，框架自带的 `SimpleAgent` 只负责“组织上下文 + 调用大模型 + 保存历史”，它本身不会解析工具调用，也不会执行工具。

我们重写的 `MySimpleAgent` 在这个基础上增加了工具能力，核心新增点有三个：

1. 引入 `tool_registry`

`tool_registry` 可以理解成 Agent 的工具箱目录。它负责保存“工具名 -> 工具对象”的映射。比如注册计算器工具后，Agent 就能通过工具名 `calculator` 找到对应工具并执行。

2. 增强系统提示词

大模型本身并不知道 Python 程序里有哪些工具，所以 `MySimpleAgent` 会通过 `_get_enhanced_system_prompt()` 把工具描述和工具调用格式写进系统提示词。

工具调用格式是：

```text
[TOOL_CALL:{tool_name}:{parameters}]
```

这一步的作用是告诉模型：

```text
你有哪些工具可以用；
如果要用工具，请按固定格式输出；
程序会识别这个格式并真正执行工具。
```

3. 增加工具调用循环

当 `enable_tool_calling` 为 `False` 时，`MySimpleAgent` 退化成普通对话 Agent：

```text
messages -> llm.invoke() -> 保存历史 -> 返回回答
```

当 `enable_tool_calling` 为 `True` 且存在 `tool_registry` 时，它会进入 `_run_with_tools()`：

```text
调用 LLM
↓
解析模型输出中是否包含 [TOOL_CALL:...]
↓
如果没有工具调用，说明这是最终回答，直接返回
↓
如果有工具调用，Python 根据工具名执行工具
↓
把工具执行结果重新追加进 messages
↓
再次调用 LLM
↓
重复直到模型不再请求工具，或达到最大工具调用轮数
```

需要注意的是：达到最大工具调用轮数时，并不是直接把工具结果原样输出。源码里会在没有 `final_response` 的情况下再调用一次 LLM，让模型基于已有上下文和工具结果生成最终回答。

所以更准确的总结是：

```text
MySimpleAgent = SimpleAgent 的对话能力 + ToolRegistry 工具管理 + 工具调用提示词 + 工具调用循环
```

它体现了第七章框架化的核心思想：Agent 不直接把工具逻辑写死在代码里，而是通过工具注册表统一管理工具；大模型只负责“决定是否要用工具并按格式表达意图”，真正的工具执行仍然由 Python 程序完成。

## 12. ReActAgent 与 MyReActAgent 的复盘

### 正确理解

`ReActAgent` 的核心思想是把推理和行动结合起来。它不是一次性让模型直接回答，而是要求模型每一步都输出：

```text
Thought: 当前思考
Action: 下一步行动
```

其中 `Action` 有两类：

```text
工具名[工具输入]        表示调用某个工具
Finish[最终答案]       表示任务完成，输出最终答案
```

所以 `ReActAgent` 的本质是：

```text
让大模型先思考，再决定是否调用工具；Python 程序执行工具后，把观察结果交还给大模型继续推理。
```

在初始化时，`MyReActAgent` 先调用父类初始化基础 Agent 能力：

```text
name
llm
system_prompt
config
_history
```

注意：父类拿到的是 `llm` 对象，不是直接拿“模型名称”。模型名称、provider、base_url 等信息在 `HelloAgentsLLM` 对象内部。

然后 `MyReActAgent` 自己额外保存：

```text
tool_registry      工具注册表
max_steps          最大执行步数
current_history    当前任务内的 ReAct 执行轨迹
prompt_template    ReAct 提示词模板
```

其中 `prompt_template` 支持用户自定义；如果用户没有传入，就使用默认的 ReAct 提示词。

### 运行流程

`MyReActAgent.run()` 的整体流程是：

```text
清空当前任务的 current_history
↓
进入 while 循环，最多执行 max_steps 步
↓
读取工具注册表中的工具描述
↓
把工具描述、用户问题、当前执行历史拼进 ReAct 提示词
↓
把提示词封装成 messages
↓
调用 llm.invoke(messages)
↓
解析模型输出中的 Thought 和 Action
↓
如果 Action 是 Finish[最终答案]，任务结束
↓
如果 Action 是 工具名[参数]，Python 调用对应工具
↓
把 Action 和工具返回的 Observation 追加进 current_history
↓
下一轮循环把新的 current_history 重新拼进提示词
```

这里的 `current_history` 不是普通多轮聊天历史，而是当前 ReAct 任务内的执行轨迹，主要保存：

```text
Action: ...
Observation: ...
```

它的作用是告诉模型：

```text
你前面已经采取过什么行动；
工具返回了什么观察结果；
下一步应该基于这些结果继续推理。
```

当模型输出：

```text
Action: Finish[最终答案]
```

程序会解析出最终答案，把用户输入和最终答案保存进 Agent 的 `_history`，然后返回结果。

如果循环达到 `max_steps` 还没有得到 `Finish[...]`，程序会返回一个失败提示：

```text
抱歉，我无法在限定步数内完成这个任务。
```

并同样把用户输入和这个最终结果保存到 `_history`。

### 易错点

1. `ReActAgent` 和 `MySimpleAgent` 的工具调用格式不同。

`MySimpleAgent` 使用：

```text
[TOOL_CALL:tool_name:parameters]
```

`ReActAgent` 使用：

```text
Action: tool_name[tool_input]
Action: Finish[最终答案]
```

2. `current_history` 和 `_history` 不是一回事。

`current_history` 是一次 ReAct 任务内部的行动轨迹，每次 `run()` 开始都会清空。

`_history` 是 Agent 的多轮对话历史，用来记录用户输入和最终回答。

3. 工具不是模型真正执行的。

模型只是在文本里输出自己想采取的行动，例如：

```text
Action: calculator[15 * 8 + 32]
```

真正解析这个文本、找到工具、执行工具的是 Python 程序和 `ToolRegistry`。

4. ReAct 的停止条件主要有两个。

```text
模型输出 Finish[最终答案]
达到 max_steps 最大步数
```

第一个表示模型认为任务完成；第二个是程序为了防止无限循环设置的安全边界。

## 13. ReflectionAgent 与 MyReflectionAgent 的复盘

### 正确理解

`ReflectionAgent` 的核心思想是“生成 -> 反思 -> 优化”。它不像 `ReActAgent` 那样重点关注工具调用，而是重点关注如何让模型对自己的输出进行评审，并根据评审意见迭代改进。

它通常适合这类任务：

```text
写文章
写代码
生成报告
优化答案
```

这些任务的特点是：第一版结果不一定最好，需要经过审查和修改。

`MyReflectionAgent` 初始化时，先调用父类保存基础 Agent 信息：

```text
name
llm
system_prompt
config
_history
```

然后自己额外保存：

```text
max_iterations    最大反思优化轮数
memory            当前任务的短期记忆
prompts           提示词模板
```

这里的 `prompts` 通常包含三类模板：

```text
initial   用来生成初稿
reflect   用来评估当前回答
refine    用来根据反馈修改回答
```

用户可以通过 `custom_prompts` 自定义这些模板。例如代码生成任务可以把 `reflect` 写成“请审查代码效率”，而文章任务可以把 `reflect` 写成“请审查文章结构和表达”。

### 运行流程

`ReflectionAgent.run()` 的整体流程是：

```text
接收用户任务
↓
清空当前任务 memory，避免上一次任务污染当前任务
↓
使用 initial 提示词生成初稿
↓
把初稿作为 execution 记录进 memory
↓
进入反思优化循环，最多执行 max_iterations 轮
↓
取出最近一次 execution
↓
使用 reflect 提示词评估当前回答
↓
把评审意见作为 reflection 记录进 memory
↓
如果评审意见包含“无需改进”，提前停止
↓
否则使用 refine 提示词，把任务、上一版回答、评审意见一起发给模型
↓
得到修改后的新版本
↓
把新版本作为 execution 记录进 memory
↓
循环结束后，取最后一次 execution 作为最终答案
↓
把用户输入和最终答案保存进 Agent 的 _history
```

可以把它理解成一个写作流程：

```text
作者先写一版
↓
编辑审稿
↓
作者根据审稿意见修改
↓
编辑再审
↓
直到编辑认为无需修改，或达到最大修改轮数
```

### 易错点

1. 评估模型不一定是另一个模型。

在当前实现里，生成初稿、评估回答、优化回答调用的都是同一个 `llm` 对象。区别不在于换了模型，而在于换了提示词：

```text
initial prompt 让模型扮演执行者
reflect prompt 让模型扮演评审者
refine prompt 让模型扮演修改者
```

2. `memory` 和 `_history` 不是一回事。

`memory` 是一次 Reflection 任务内部的短期轨迹，保存每轮生成结果和反思反馈：

```text
execution
reflection
execution
reflection
...
```

`_history` 是 Agent 的多轮对话历史，只在任务结束后保存用户输入和最终答案。

3. 停止条件有两个。

```text
评审反馈中出现“无需改进”
达到 max_iterations 最大迭代轮数
```

如果模型一直认为需要继续优化，程序也不会无限循环，因为 `max_iterations` 提供了安全上限。

4. 最终答案不是最后一次 reflection。

最终答案取的是最后一次 `execution`，也就是最后一版生成或修改后的结果；`reflection` 只是评审意见，不是最终交给用户的答案。

## 14. PlanAndSolveAgent 与 MyPlanAndSolveAgent 的复盘

### 正确理解

`PlanAndSolveAgent` 的核心思想是“先规划，再执行”。它适合处理多步骤任务，尤其是那些直接让模型回答容易漏步骤、算错或逻辑混乱的问题。

它把任务拆成两个角色：

```text
Planner   规划器：负责把复杂问题拆成步骤列表
Executor  执行器：负责按照计划一步一步完成任务
```

规划器和执行器当前使用的是同一个 `llm` 对象。区别不在于换了模型，而在于使用了不同的提示词模板：

```text
planner prompt   让模型扮演规划专家
executor prompt  让模型扮演执行专家
```

### 运行流程

`MyPlanAndSolveAgent.run()` 的整体流程是：

```text
接收用户问题
↓
把问题填入 planner 提示词
↓
调用 llm.invoke() 生成计划
↓
要求模型把计划输出成 Python 列表格式
↓
用 ast.literal_eval() 把模型输出解析成真正的 Python list
↓
如果计划解析失败或为空，任务终止
↓
如果计划有效，把问题和计划交给 Executor
↓
Executor 按计划逐步执行
↓
每一步都构建 executor 提示词
↓
提示词中包含：原始问题、完整计划、历史步骤与结果、当前步骤
↓
调用 llm.invoke() 得到当前步骤结果
↓
把当前步骤和结果追加进 history
↓
执行完所有步骤后，返回最后一步的结果作为最终答案
↓
把用户问题和最终答案保存进 Agent 的 _history
```

其中 Planner 的输出被要求是这种格式：

```python
["步骤1", "步骤2", "步骤3"]
```

这样程序才能把模型生成的文本解析成列表，然后交给 Executor 循环执行。

Executor 每一步拿到的信息包括：

```text
原始问题
完整计划
已经完成的步骤和结果
当前要执行的步骤
```

所以它不是孤立地执行某一步，而是在知道整体目标和前面结果的基础上完成当前步骤。

### 易错点

1. Plan-and-Solve 不是工具调用范式。

它的重点不是让模型选择工具，而是先把复杂问题拆成步骤，再按步骤调用模型完成。当前实现里没有 `ToolRegistry`，也没有真正执行外部工具。

2. Planner 和 Executor 不一定是两个不同模型。

当前代码里二者共用同一个 `llm`，只是提示词不同。也就是说：

```text
同一个模型 + 不同提示词 = 不同角色
```

3. 计划必须能被解析。

Planner 被要求输出 Python 列表，是为了让程序能用 `ast.literal_eval()` 安全解析。如果模型没有按格式输出，计划解析会失败，Agent 会返回：

```text
无法生成有效的行动计划，任务终止。
```

4. 最终答案是最后一步执行结果。

当前实现中，Executor 每执行一步都会更新 `final_answer`，最后返回的是最后一个步骤的结果。它不是额外再调用一次模型对所有步骤做总总结。

5. `history` 和 `_history` 不是一回事。

Executor 里的 `history` 是执行计划过程中的步骤结果记录，用来给后续步骤提供上下文。

Agent 的 `_history` 是对话历史，只在任务结束后保存用户问题和最终答案。

## 15. Function Calling 与工具系统复盘

### 正确理解

第七章后半部分开始把“工具调用”从临时字符串解析，推进到更统一的工具系统。

早期 Agent 调工具常见做法是让模型输出类似这样的文本：

```text
Action: calculator[15 * 8 + 32]
```

或者：

```text
[TOOL_CALL:calculator:15 * 8 + 32]
```

然后 Python 程序用正则或字符串解析模型输出，判断要调用哪个工具、传什么参数。

这种方式能跑，但不够稳定。因为模型可能少写括号、格式不标准、混入解释文字，导致解析失败。

标准 function calling 的目标是让模型按结构化格式表达“我要调用哪个函数，以及参数是什么”。通常会让模型返回 JSON 结构，例如：

```json
{
  "name": "calculator",
  "arguments": {
    "expression": "15 * 8 + 32"
  }
}
```

这样程序可以直接把 JSON 转成字典，然后稳定地取出：

```text
函数名
参数名
参数值
```

所以 function calling 的核心价值是：

```text
用结构化数据替代自然语言解析，提高工具调用的稳定性。
```

### Tool 抽象

第七章定义了一个抽象工具类 `Tool`，用来统一所有工具的接口。

工具基类主要包含：

```text
name           工具名称
description    工具描述
run()          执行工具
get_parameters() 获取工具参数定义
```

其中 `run()` 和 `get_parameters()` 是抽象方法，子类必须实现。

这背后的设计思想是：

```text
所有工具都必须以统一方式被框架调用。
```

也就是说，不管是计算器、搜索工具、记忆工具，还是后续自定义工具，Agent 和工具注册表都希望它们看起来像这样：

```python
result = tool.run(parameters)
```

工具参数一般用字典承载，工具结果统一返回字符串。这会让上层 Agent 不需要关心每个工具内部到底怎么实现。

### ToolParameter

`ToolParameter` 用来描述一个工具参数，例如：

```text
参数名
参数类型
参数描述
是否必填
默认值
```

它的作用是让工具能够清楚说明自己需要什么输入。

例如计算器工具可能需要：

```text
expression: string，数学表达式，必填
```

这类参数描述后续可以用于生成工具说明，也可以进一步转换为更标准的 function calling schema。

### ToolRegistry 工具注册表

`ToolRegistry` 可以理解成 Agent 的工具管理中心。

它负责：

```text
注册工具
注册普通函数为工具
注销工具
按名称获取工具
执行指定工具
列出所有可用工具
生成工具描述文本
```

它支持两种注册方式。

第一种是注册 `Tool` 对象：

```python
registry.register_tool(calculator_tool)
```

这种方式更正式，适合复杂工具。工具本身需要继承 `Tool`，实现 `run()` 和 `get_parameters()`。

第二种是直接注册函数：

```python
registry.register_function(
    name="my_calculator",
    description="简单的数学计算工具",
    func=my_calculate
)
```

这种方式更轻量，适合把一个普通 Python 函数快速包装成工具。

注册后，程序可以通过统一入口执行工具：

```python
registry.execute_tool("my_calculator", "15 * 8 + 32")
```

这样 Agent 不需要直接调用具体函数，而是通过工具注册表按名称查找和执行。

### 自定义计算工具

第七章示例里自定义了一个计算工具函数：

```python
def my_calculate(expression: str) -> str:
    ...
```

它接收数学表达式字符串，返回计算结果字符串。

然后用 `register_function()` 注册成工具：

```python
registry.register_function(
    name="my_calculator",
    description="简单的数学计算工具，支持基本运算(+,-,*,/)和sqrt函数",
    func=my_calculate
)
```

注册完成后，Agent 或测试代码就可以通过注册器执行它。

这个例子说明：

```text
工具不一定一开始就要写成复杂类；
简单函数也可以先注册成工具；
等工具逻辑复杂后，再升级为 Tool 子类。
```

### 类方法注册为工具

后面还演示了把一个类中的方法注册为工具。

这适合那些需要维护状态的工具。例如搜索工具可能需要保存 API 客户端、搜索源配置、缓存等信息。

函数工具适合简单无状态逻辑：

```text
输入 -> 处理 -> 输出
```

类工具适合复杂有状态逻辑：

```text
初始化配置
↓
保存客户端或状态
↓
调用类方法完成任务
```

### 易错点

1. Function calling 和普通文本工具调用不是一回事。

普通文本工具调用依赖模型输出固定格式文本，然后程序解析文本。

Function calling 更强调结构化输出，例如 JSON，程序可以稳定解析成字典或列表。

2. 当前 `hello-agents==0.1.1` 的工具注册表仍然比较轻量。

本地源码里的 `ToolRegistry` 已经支持工具注册、函数注册、工具描述和工具执行，但还不是一个完整复杂的 OpenAI function calling schema 管理器。

所以这里要区分：

```text
概念上：工具参数可以对接 function calling schema
当前代码里：主要还是通过 Tool / ToolRegistry 统一管理和执行工具
```

3. 模型不真正执行函数。

不管是文本格式还是 JSON 格式，模型只是表达“我想调用什么函数，以及参数是什么”。真正执行函数的是 Python 程序。

4. 统一接口是工具系统的重点。

`Tool` 抽象类要求所有工具实现 `run()` 和 `get_parameters()`，目的是让框架可以用一致的方式管理不同工具，而不是每个工具都写一套特殊调用逻辑。

## 16. 工具系统高级特性复盘

### 正确理解

第七章最后介绍了两个工具系统的高级特性：

```text
工具链式调用机制
异步工具执行支持
```

前者解决“多个工具需要按顺序组合使用”的问题，后者解决“多个慢工具可以并发执行，减少等待时间”的问题。

### 工具链式调用

`ToolChain` 可以理解成一个固定流程的工具调用管道。

它内部保存多个步骤，每个步骤包含：

```text
tool_name        要调用的工具名
input_template   该工具的输入模板
output_key       该步骤输出结果保存到上下文中的 key
```

添加步骤时使用：

```python
chain.add_step(
    tool_name="search",
    input_template="{input}",
    output_key="search_result"
)
```

执行工具链时，会先初始化一个上下文：

```text
context["input"] = 用户初始输入
```

然后按顺序执行每个步骤：

```text
读取当前步骤 input_template
↓
用 context 替换模板变量
↓
调用 registry.execute_tool(tool_name, actual_input)
↓
把工具输出保存到 context[output_key]
↓
下一个步骤可以通过 {output_key} 引用前一步结果
```

所以工具链的关键不是简单地“一个工具调完再调下一个”，而是：

```text
上一步工具的输出可以成为下一步工具的输入。
```

`ToolChainManager` 则是工具链管理器，负责：

```text
注册工具链
按名称执行工具链
列出已有工具链
查看工具链信息
```

可以类比：

```text
ToolRegistry 管理单个工具
ToolChainManager 管理一组已经编排好的工具流程
```

### 异步工具执行

有些工具执行很慢，例如：

```text
搜索
查天气
请求外部 API
读取远程数据
```

如果多个慢工具线性执行，总耗时会变成每个工具耗时之和。

异步工具执行器 `AsyncToolExecutor` 的目标是让多个工具任务尽量并发执行，从而减少总等待时间。

它的核心结构是：

```python
self.executor = ThreadPoolExecutor(max_workers=max_workers)
```

因为 `ToolRegistry.execute_tool()` 是同步阻塞函数，所以代码会把它包进一个内部函数：

```python
def _execute():
    return self.registry.execute_tool(tool_name, input_data)
```

然后用：

```python
await loop.run_in_executor(self.executor, _execute)
```

把同步工具调用丢到线程池里执行。这样异步函数本身不会一直阻塞事件循环。

批量执行时，每个任务包含：

```text
tool_name
input_data
```

理想的并行流程应该是：

```text
为每个工具调用创建异步任务
↓
把所有任务交给 event loop 调度
↓
等待所有任务完成
↓
统一收集结果
```

### 易错点

1. 工具链是顺序执行，不是并行执行。

工具链的重点是“上一步结果传给下一步”，所以它通常必须按顺序执行。

2. 异步工具执行适合 I/O 密集型任务。

例如网络请求、搜索、查天气、读写文件等。对于很重的 CPU 计算，线程池不一定能显著提升性能。

3. 第七章文章中的并行实现使用了 `asyncio.gather()`。

第七章正文里的 `execute_tools_parallel()` 会先为每个工具任务创建一个协程：

```python
async_task = self.execute_tool_async(tool_name, input_data)
async_tasks.append(async_task)
```

然后用：

```python
results = await asyncio.gather(*async_tasks)
```

统一等待所有协程执行完成。

所以文章中的并行逻辑可以理解为：

```text
为每个工具调用创建协程
↓
用 asyncio.gather() 把所有协程一起交给事件循环调度
↓
每个协程内部再通过 run_in_executor() 把同步工具调用放到线程池执行
↓
所有任务完成后统一返回结果列表
```

所以这里要区分：

```text
execute_tool_async()：负责把单个同步工具调用包装成异步执行
execute_tools_parallel()：负责把多个异步工具任务并发调度起来
```

4. 异步执行后要释放资源。

`AsyncToolExecutor` 内部创建了线程池，所以执行结束后应该调用 `close()`，或使用上下文管理器，确保线程池被关闭。
