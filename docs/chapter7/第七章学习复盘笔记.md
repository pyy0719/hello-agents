# 第七章学习复盘笔记

> 这份笔记不是照抄教材，而是根据我自己的提问、卡点和理解过程整理出来的。后续继续学习第七章时，可以不断往这里追加。

## 1. 从第一章手写 Agent 回看 Agent 的本质

第一章里的 Agent 并不是一个神秘的东西，它本质上是一段 Python 控制流程。

最朴素的 Agent 可以理解成：

```text
Agent = 大模型 + 工具 + 一套循环流程
```

第一章的基本流程是：

```text
准备系统提示词
↓
把用户问题和提示词一起发给大模型
↓
大模型输出 Thought / Action / Action Input / Final Answer
↓
Python 程序解析大模型输出
↓
如果是 Action，就调用对应工具
↓
把工具结果追加进上下文
↓
再次把完整上下文发给大模型
↓
直到识别到 Final Answer，结束任务
```

这里最重要的一点是：大模型本身不会持续运行，也不会真的自己记住上一轮发生了什么。每次调用大模型时，它只知道这次请求里传进去的内容。

所以所谓“上下文”，其实是 Python 程序帮大模型维护的一段越来越长的文本或消息列表。

也就是说：

```text
大模型负责根据上下文生成下一步文本。
Python 程序负责判断文本、调用工具、维护上下文、决定是否继续循环。
```

## 2. 为什么需要框架

手写 Agent 可以帮助理解原理，但功能一多，代码会开始重复和混乱。

常见重复点包括：

- 每个 Agent 都要重复写调用大模型的代码。
- 每个 Agent 都要自己维护上下文和历史消息。
- 每个工具都要自己规定输入、输出和错误处理。
- ReAct、Reflection、Plan-and-Solve 等范式会重复写类似控制流程。
- 换 OpenAI、DeepSeek、通义、本地模型时，配置容易散落在各处。

所以框架的作用不是“显得高级”，而是把容易重复、容易出错的部分抽象成统一组件。

HelloAgents 大致把这些东西拆成：

```text
HelloAgentsLLM   统一调用大模型
Agent            智能体基类
SimpleAgent      简单对话智能体
ReActAgent       推理 + 行动智能体
ReflectionAgent  反思优化智能体
ToolRegistry     工具注册表
Message          统一消息格式
Config           配置管理
```

可以理解成：

```text
上层 Agent 不直接关心模型厂商、工具细节、消息结构。
框架把这些部分整理好，让 Agent 更专注于“如何完成任务”。
```

## 3. 第四章的 HelloAgentsLLM 是什么

第四章先实现了一个简单版的大模型客户端 `HelloAgentsLLM`。

它的作用是：

```text
封装底层大模型 API 调用，让 Agent 不直接依赖 OpenAI SDK。
```

第四章的结构大致是：

```python
class HelloAgentsLLM:
    def __init__(self, model=None, apiKey=None, baseUrl=None, timeout=None):
        self.model = model or os.getenv("LLM_MODEL_ID")
        apiKey = apiKey or os.getenv("LLM_API_KEY")
        baseUrl = baseUrl or os.getenv("LLM_BASE_URL")
        self.client = OpenAI(api_key=apiKey, base_url=baseUrl, timeout=timeout)

    def think(self, messages, temperature=0):
        response = self.client.chat.completions.create(...)
        return response_text
```

这里的 `OpenAI` 不是 Agent，也不是大模型本身，而是 OpenAI Python SDK 提供的客户端类。

可以把它理解成：

```text
OpenAI SDK 客户端 = 负责向模型服务发送 HTTP 请求的工具
```

虽然它叫 `OpenAI`，但不一定只能调用 OpenAI 官方模型。很多模型服务商都兼容 OpenAI 接口格式，例如 DeepSeek、通义、Kimi、Ollama、vLLM 等。

所以调用链可以理解为：

```text
Agent
↓
HelloAgentsLLM
↓
OpenAI SDK 客户端
↓
DeepSeek / OpenAI / 其他兼容服务
```

这层封装的价值是：Agent 只需要调用 `llm.think(messages)`，不用关心底层请求细节。

## 4. 第七章对 HelloAgentsLLM 做了什么升级

第七章是在第四章简单客户端的基础上继续升级。

主要升级点是：

- 支持多个模型提供商。
- 支持自动检测 provider。
- 支持本地模型服务，例如 Ollama、vLLM。
- 提供统一的 `invoke()`、`think()`、`stream_invoke()` 调用方法。

第七章里的初始化参数大致是：

```python
def __init__(
    self,
    model: Optional[str] = None,
    api_key: Optional[str] = None,
    base_url: Optional[str] = None,
    provider: Optional[str] = "auto",
    **kwargs
):
```

其中 `Optional[str]` 表示这个参数可以是字符串，也可以是 `None`。

例如：

```python
model: Optional[str] = None
```

意思是：

```text
model 可以传字符串，比如 "deepseek-chat"；
也可以不传，不传时就是 None。
```

不传时，程序通常会去 `.env` 或默认配置里找。

## 5. provider 到底是什么

`provider` 可以理解成“模型服务商”或“模型来源”的标签。

例如：

```text
openai      OpenAI 官方
deepseek    DeepSeek
qwen        通义千问 / DashScope
modelscope  ModelScope
kimi        Moonshot / Kimi
zhipu       智谱
ollama      本地 Ollama
vllm        本地 vLLM 服务
local       其他本地服务
```

它不只是一个普通名字，而是一个配置选择开关。

因为不同服务商需要不同的默认配置：

```text
DeepSeek:
api_key 可能来自 DEEPSEEK_API_KEY 或 LLM_API_KEY
base_url 默认 https://api.deepseek.com
model 默认 deepseek-chat

OpenAI:
api_key 可能来自 OPENAI_API_KEY 或 LLM_API_KEY
base_url 默认 https://api.openai.com/v1
model 默认 gpt-3.5-turbo

Ollama:
api_key 可以是 ollama
base_url 默认 http://localhost:11434/v1
model 默认 llama3.2
```

所以：

```python
HelloAgentsLLM(provider="deepseek")
```

意思是告诉框架：

```text
请按 DeepSeek 的规则去解析 key、url 和默认模型。
```

注意：

```text
provider 这个参数名是代码作者起的，理论上可以改，但全项目都要跟着改。
provider 的值如 "deepseek"、"openai" 是框架约定好的，不能随便乱写。
```

## 6. provider="deepseek" 时源码里发生了什么

当代码写成：

```python
llm = HelloAgentsLLM(provider="deepseek")
```

执行顺序大致是：

```text
1. 进入 HelloAgentsLLM.__init__()
2. 读取 model：优先用传入参数，其次用 LLM_MODEL_ID
3. 因为手动传入 provider="deepseek"，所以不会走自动检测
4. 调用 _resolve_credentials()
5. 进入 deepseek 分支
6. 解析 api_key 和 base_url
7. 如果没有模型名，使用默认模型 deepseek-chat
8. 创建 OpenAI SDK 客户端
```

DeepSeek 分支的核心逻辑是：

```python
resolved_api_key = api_key or os.getenv("DEEPSEEK_API_KEY") or os.getenv("LLM_API_KEY")
resolved_base_url = base_url or os.getenv("LLM_BASE_URL") or "https://api.deepseek.com"
```

意思是：

```text
api_key 优先级：
手动传入 api_key
↓
DEEPSEEK_API_KEY
↓
LLM_API_KEY

base_url 优先级：
手动传入 base_url
↓
LLM_BASE_URL
↓
https://api.deepseek.com
```

真正调用模型时，会执行：

```python
self._client.chat.completions.create(
    model=self.model,
    messages=messages,
    ...
)
```

虽然这里用的是 OpenAI SDK，但请求实际会发到 `base_url` 指向的 DeepSeek 服务。

## 7. 自动检测 provider 的坑

只有不传 provider 时，才会自动检测：

```python
llm = HelloAgentsLLM()
```

源码中自动检测的顺序大致是：

```text
1. 如果有 OPENAI_API_KEY，返回 openai
2. 如果有 DEEPSEEK_API_KEY，返回 deepseek
3. 如果有 DASHSCOPE_API_KEY，返回 qwen
4. 如果有 MODELSCOPE_API_KEY，返回 modelscope
5. 再根据 LLM_API_KEY 格式判断
6. 再根据 LLM_BASE_URL 判断
7. 都判断不出来，返回 auto
```

我在 Windows 上遇到的问题是：

```text
.env 里配置的是 DeepSeek 的 LLM_API_KEY，
但系统环境变量里已经存在一个旧的 OPENAI_API_KEY。
```

因为自动检测优先检查 `OPENAI_API_KEY`，所以框架误判成了 `openai`，并拿旧 key 去请求，导致 401。

解决方式：

```python
llm = HelloAgentsLLM(provider="deepseek")
```

这样可以绕开自动检测，强制走 DeepSeek 分支。

## 8. 本地模型调用：Ollama 和 vLLM 是否必须装

第七章提到了本地模型调用，主要是为了说明：除了调用云端 API，也可以把模型部署在本地。

本地部署的价值主要有：

- 隐私：数据不发给外部服务商。
- 成本：不再按 API token 计费，但要承担硬件、电费和维护成本。
- 可控性：可以自己选择模型、部署方式、上下文长度和日志策略。

但本地部署不是“完全没有成本”，而是成本结构变化了。

可以类比为：

```text
调用 API = 打车，每次付钱，但不用维护车。
本地部署 = 买车，不按每次出行付费，但要买车、加油、保养。
```

对当前学习第七章来说，不需要安装 Ollama 或 vLLM。

当前最稳学习配置是：

```text
使用 DeepSeek API 跑通 HelloAgentsLLM
↓
理解 Agent 如何调用 LLM
↓
理解 SimpleAgent / ReActAgent / ReflectionAgent
↓
理解 ToolRegistry 和工具调用
↓
以后遇到隐私、成本、高并发问题，再学习本地模型部署
```

## 9. BaseModel 是什么

`BaseModel` 通常来自 Pydantic：

```python
from pydantic import BaseModel
```

它可以理解成：

```text
一个带自动校验能力的数据类基类。
```

普通 Python 类只是装数据，不会主动检查类型。

而继承 `BaseModel` 后，可以定义稳定的数据结构：

```python
class Message(BaseModel):
    role: str
    content: str
```

这表示：

```text
Message 必须有 role 和 content 两个字段；
它们都应该是字符串。
```

在 Agent 框架里，消息格式非常重要，因为大模型 API 需要类似这样的结构：

```python
[
    {"role": "system", "content": "你是一个助手"},
    {"role": "user", "content": "你好"},
    {"role": "assistant", "content": "你好，有什么可以帮你？"}
]
```

使用 `BaseModel` 定义 `Message` 的好处是：

- 保证消息结构统一。
- 自动检查字段类型。
- 方便转成 dict 或 json。
- 减少由于字段乱写导致的错误。

一句话总结：

```text
BaseModel 用来定义可靠的数据结构；在 Agent 框架中，它帮助 Message、Config、Tool 参数等对象保持格式稳定。
```

## 10. 当前阶段我的理解总结

目前我对第七章主线的理解是：

```text
第一章：手写 Agent，理解 Agent 是一个循环。
第四章：封装 HelloAgentsLLM，统一大模型调用。
第七章：把 LLM、Agent、Message、Tool 等组件框架化。
```

其中：

```text
HelloAgentsLLM 负责连接模型服务。
provider 决定按哪个模型服务商的规则解析配置。
OpenAI SDK 是底层请求工具，不等于只能调用 OpenAI。
Message 用来统一大模型对话消息格式。
BaseModel 用来保证数据结构可靠。
Agent 负责组织任务流程、维护上下文、调用 LLM 和工具。
```

后续继续学习时，可以重点补充：

- `Message` 类的完整设计。
- `Config` 配置类。
- `Agent` 基类为什么要设计成抽象类。
- `SimpleAgent` 的运行流程。
- `ToolRegistry` 工具注册机制。
- ReActAgent、ReflectionAgent、PlanAndSolveAgent 的差异。
