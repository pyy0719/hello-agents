# 第八章学习复盘笔记

## 1. 记忆模块整体结构

第 8 章的记忆模块可以理解为三层结构：

```text
Agent
↓
MemoryTool
↓
MemoryManager
↓
WorkingMemory / EpisodicMemory / SemanticMemory / PerceptualMemory
```

`MemoryTool` 是暴露给 Agent 的统一记忆工具接口。Agent 不需要直接关心每种记忆的底层实现，只需要通过 `MemoryTool` 调用添加、搜索、统计、整合、遗忘等操作。

`MemoryManager` 是记忆系统的调度中心。它负责根据 `memory_type` 把请求分发给具体的记忆类型，例如工作记忆、情景记忆、语义记忆或感知记忆。

`MemoryTool` 的操作可以大致分成三类：

- 添加类：`add`
- 检索类：`search`、`summary`、`stats`
- 管理类：`update`、`remove`、`forget`、`consolidate`、`clear_all`

所以，不能简单说 `MemoryTool` 只支持三种操作。更准确的说法是：它支持多种 action，但这些 action 可以归纳为添加、检索和管理三大类。

## 2. WorkingMemory：工作记忆

`WorkingMemory` 是短期工作记忆，主要存放当前任务中的临时上下文。

它的特点是：

- 轻量
- 快速
- 短期有效
- 通常保存在内存中
- 通过 TTL 自动清理过期数据

适合保存的信息包括：

- 当前对话上下文
- 当前任务状态
- 临时变量
- 用户刚刚说过但不一定需要长期保存的信息

工作记忆检索时会考虑关键词匹配、相关性、重要性和时间衰减等因素。它的重点不是像 Qdrant 那样做复杂向量数据库检索，而是快速找回当前任务附近的临时信息。

当一条工作记忆反复出现、重要性很高、用户明确要求记住，或者对未来长期有价值时，可以通过 `consolidate` 将它整合为长期记忆。

## 3. EpisodicMemory：情景记忆

`EpisodicMemory` 是情景记忆，用来记录具体发生过的事件。

它适合保存：

- 某次对话中发生了什么
- 用户什么时候问过什么问题
- 用户什么时候完成了某个任务
- 某次学习、调试、运行结果

情景记忆采用 SQLite + Qdrant 的混合架构：

- SQLite：保存完整事件内容和结构化字段
- Qdrant：保存向量，用于语义检索

添加情景记忆时，系统会把事件内容、时间、用户 ID、会话 ID、重要性等信息保存下来，同时生成向量写入 Qdrant。

检索情景记忆时，通常会先做结构化过滤，例如：

- `user_id`
- `session_id`
- 时间范围
- 重要性

然后再做语义向量检索，并综合计算最终分数：

```text
最终分数 = 语义相似度 + 时间近因性 + 重要性权重
```

情景记忆更强调时间近因性，因为它记录的是事件。对于事件来说，最近发生的事情通常更可能影响当前任务。

## 4. SemanticMemory：语义记忆

`SemanticMemory` 是语义记忆，用来保存长期稳定的知识、概念、事实和关系。

它适合保存：

- 用户画像
- 长期偏好
- 领域知识
- 概念关系
- 事实性信息

添加语义记忆时，流程大致是：

```text
文本内容
↓
生成 embedding 向量
↓
使用 NLP 处理器抽取实体和关系
↓
实体和关系存入 Neo4j
↓
向量和元数据存入 Qdrant
```

这里要分清楚：

- Neo4j 存的是实体、关系和知识图谱结构
- Qdrant 存的是文本向量和元数据

所以不是把“向量化后的文本”存入 Neo4j。Neo4j 负责图关系，Qdrant 负责语义向量检索。

语义记忆检索时会结合：

- Qdrant 向量检索
- Neo4j 图检索
- 重要性权重

这种混合检索让系统既能找语义相似内容，也能做实体关系推理。

## 5. PerceptualMemory：感知记忆

`PerceptualMemory` 是感知记忆，用来处理文本、图像、音频等多模态信息。

多模态的意思是：信息不只来自文本，还可以来自图片、音频等不同类型的数据。

不同模态会使用不同的编码器：

- 文本：文本 embedding 编码器
- 图像：图像编码器
- 音频：音频编码器

感知记忆支持两种检索方式：

- 同模态检索：文本搜文本、图片搜图片、音频搜音频
- 跨模态检索：文本搜图片、文本搜音频、图片搜文本等

同模态检索主要依赖对应模态的专业编码器进行匹配。跨模态检索更复杂，需要不同模态之间有统一或可对齐的语义空间。

感知记忆的评分通常会综合：

```text
向量相似度 + 时间近因性 + 重要性权重
```

其中，时间近因性表示越新的记忆在检索排序中越容易靠前；越旧的记忆分数会逐渐衰减，但不一定立刻被删除。

## 6. 记忆管理：整合与遗忘

记忆管理主要包括整合和遗忘。

整合是指把重要的短期工作记忆转化为长期记忆。例如，某条工作记忆反复出现、重要性评分较高、被用户明确要求记住，或者对未来任务有长期价值，就可以被整合为情景记忆或语义记忆。

遗忘是指清理不再需要的记忆。常见策略包括：

- 基于重要性：优先删除重要性低的记忆
- 基于时间：删除超过保存期限的记忆
- 基于容量：当存储达到上限时，优先删除最不重要或最少访问的记忆

遗忘不只是简单删除文本。对于使用 SQLite、Qdrant、Neo4j 的系统，同一条记忆可能同时存在于结构化数据库、向量数据库和图数据库中。因此真正删除时，需要同时清理原始记录、向量点、图节点或图关系。

## 7. 本节核心总结

第 8 章记忆模块的核心是：通过 `MemoryTool` 给 Agent 暴露统一记忆能力，通过 `MemoryManager` 调度不同记忆类型，再由不同记忆实现分别处理短期上下文、事件记录、长期知识和多模态感知信息。

四类记忆的定位可以这样记：

```text
WorkingMemory：当前任务的临时便签
EpisodicMemory：发生过的事件档案
SemanticMemory：长期知识和关系网络
PerceptualMemory：文本、图像、音频等感知信息
```

最容易混淆的是存储后端：

```text
SQLite：保存完整结构化记录
Qdrant：保存向量，负责语义相似检索
Neo4j：保存实体和关系，负责图谱推理
```

## 8. RAG 模块整体流程

RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。它的核心思想是：模型回答问题前，先从外部知识库中检索相关内容，再把检索结果作为上下文交给大模型生成答案。

所以 RAG 需要先有数据。没有被处理和索引的数据，就没有后面的检索增强。

RAG 的完整流程可以分成两大阶段：

```text
数据处理阶段：原始文档 → Markdown转换 → 智能分块 → 向量化 → 存入向量数据库
查询检索阶段：用户问题 → 查询扩展/向量检索 → 召回相关chunk → 交给大模型生成回答
```

## 9. RAG 的数据处理流程

数据处理流程的第一步是文档预处理。

HelloAgents 使用 MarkItDown 将不同格式的文档统一转换为 Markdown。这样做的好处是：不管原始输入是 PDF、Word、Excel、图片、音频还是普通文本，后续流程都可以统一处理 Markdown，而不需要为每种格式单独写一套分块和索引逻辑。

本章的实现中，对 PDF 做了增强处理。因为 PDF 经常包含复杂排版、表格、图片、多栏文本、页眉页脚等内容，直接读取容易出现顺序错乱或内容丢失，所以 PDF 会走专门的增强处理流程。

文档转换完成后，会进入智能分块阶段。

智能分块不是简单地按固定字数切开，而是会利用 Markdown 的标题结构，例如 `#`、`##`、`###`，根据章节和段落边界切分内容。这样切出来的 chunk 更容易保持语义完整。

每个 chunk 的生成还要参考最大 token 数量。chunk 不能太大，否则不方便向量化和检索；也不能太碎，否则语义不完整。为了避免上下文在切分边界处断裂，相邻 chunk 之间还会保留一定的重叠部分，也就是 overlap。

可以把智能分块理解为：

```text
Markdown文档
↓
识别标题层级
↓
按段落和语义边界切分
↓
控制每个chunk的最大token数
↓
给相邻chunk保留重叠内容
↓
得到适合检索的小知识块
```

## 10. 统一嵌入与向量存储

分块完成后，每个 chunk 还是普通文本。为了让系统能根据语义相似度检索它们，需要把文本转换成向量，这一步叫 embedding。

HelloAgents 会获取统一的文本嵌入模型，然后对 chunk 文本进行向量化。这里的“统一”指的是：上层流程不需要关心底层具体用的是百炼 API、本地 Transformer，还是其他 embedding 方案，只要能通过统一接口把文本变成向量即可。

向量化之前，系统会对 Markdown 文本做预处理，让文本更适合 embedding。比如清理无关格式、保留有用标题信息等。

向量生成后，系统会检查向量质量，尤其是维度是否正确。因为 Qdrant 中同一个 collection 的向量维度必须一致。

如果生成的向量维度太短，系统会补 `0.0`；如果维度太长，系统会截断到目标维度。这是一种兜底策略。更理想的情况是从一开始就保证 embedding 模型输出维度和 Qdrant collection 的维度一致。

最后，系统会把 chunk 的向量和元数据存入 Qdrant。元数据通常包括：

- chunk 内容
- 文档 ID
- 标题路径
- 起止位置
- rag namespace
- memory type 或数据来源

这样后续检索时，Qdrant 不只返回相似度分数，还能告诉我们命中的是哪个文档里的哪一段。

## 11. RAG 的高级检索策略

RAG 的检索阶段不是只能拿用户原问题直接搜。第 8 章介绍了几种高级检索策略，用来提高召回率和准确性。

第一种是 MQE，多查询扩展。

MQE 会调用大模型，把用户的原始问题改写成多个语义相近但表达不同的查询。比如用户问“怎么学 Python”，系统可以扩展为“Python入门教程”“Python学习路线”“Python基础语法”等。这样做可以减少因为用户问法和文档用词不同而导致的漏检。

第二种是 HyDE，假设文档嵌入。

HyDE 的思路是“用可能的答案去找真实答案”。它会先让大模型根据用户问题生成一段假设性的答案文本，再把这段答案文本向量化后去检索真实文档。因为文档通常是陈述句，而用户问题通常是疑问句，用答案式文本去检索，可能更接近真实文档的表达。

第三种是扩展检索框架。

扩展检索框架把原始查询、MQE 生成的扩展查询、HyDE 生成的假设文档统一放到一个检索流程里。它的核心机制是：

```text
扩展 → 检索 → 合并
```

具体来说：

```text
原始query
↓
根据配置决定是否启用 MQE
↓
根据配置决定是否启用 HyDE
↓
得到多个扩展查询
↓
为每个查询做向量检索
↓
扩大候选池
↓
按 memory_id 或 chunk_id 去重
↓
保留更高分结果
↓
排序后返回 top-k
```

其中 `candidate_pool_multiplier` 用来扩大候选池。比如最终只需要返回 5 条结果，但系统可以先检索 20 条或更多候选，再通过去重和分数排序选出最终结果。这样可以提高召回率。

如果不启用 MQE 和 HyDE，系统也可以退回普通向量检索。也就是说，高级检索是增强能力，不是必需能力。

## 12. RAG 模块核心总结

RAG 模块可以这样记：

```text
先建库，再检索，再生成。
```

建库阶段：

```text
原始文档 → MarkItDown转Markdown → 智能分块 → embedding向量化 → 存入Qdrant
```

检索阶段：

```text
用户问题 → 普通检索 / MQE / HyDE / 扩展检索 → 命中相关chunk → 交给LLM生成回答
```

最关键的几个概念是：

```text
MarkItDown：把多格式文档统一转成Markdown
chunk：适合检索的小知识块
overlap：相邻chunk之间的重叠内容，用来保持上下文连续
embedding：把文本变成向量
Qdrant：保存向量并做相似度检索
MQE：把一个问题扩展成多个问法
HyDE：先生成假设答案，再用答案去检索
扩展检索框架：把多种查询结果合并、去重、排序
```

## 13. 为什么智能体需要记忆和 RAG

第 8 章一开始从认知科学讲起，是为了说明：智能体如果只有当前上下文窗口，就很难形成稳定的长期能力。

没有记忆时，Agent 容易遇到这些问题：

- 上下文丢失：早期对话会因为上下文窗口限制被挤掉
- 个性化缺失：无法长期记住用户偏好、习惯和需求
- 学习能力受限：无法从过往成功或失败经验中改进
- 一致性问题：多轮对话中可能前后矛盾

RAG 解决的是另一类问题：

- 大模型训练数据有截止时间，知识可能过时
- 通用模型缺少专业领域知识
- 直接回答容易产生幻觉
- 检索结果可以提供信息来源，提高可解释性

所以，记忆和 RAG 是互补关系：

```text
Memory：记住用户和交互历史
RAG：检索外部知识库和文档内容
```

如果用户问“我之前学过什么”，应该优先查 Memory；如果用户问“这篇 PDF 里怎么解释 Transformer”，应该优先查 RAG。

## 14. 记忆生命周期

本章把记忆系统拆成五个阶段：

```text
编码 → 存储 → 检索 → 整合 → 遗忘
```

编码是把信息转换成可存储的形式。比如把文本变成结构化字段、embedding 向量、实体关系等。

存储是把编码后的信息保存起来。不同记忆类型会使用不同存储方式，例如内存、SQLite、Qdrant、Neo4j。

检索是根据当前任务从记忆中找回相关信息。检索时通常会考虑语义相似度、关键词匹配、时间近因性、重要性权重等因素。

整合是把短期记忆转为长期记忆。比如把重要的工作记忆转成情景记忆，或者把多次出现的事件总结成语义记忆。

遗忘是删除不重要、过期或超出容量限制的信息。遗忘不是缺陷，而是控制记忆质量和存储成本的重要机制。

## 15. RAGTool 的统一接口

`RAGTool` 是 RAG 系统暴露给 Agent 的统一工具接口，作用类似于记忆系统里的 `MemoryTool`。

它把复杂的 RAG 流程封装成几个简单 action：

- `add_document`：添加文档
- `add_text`：添加文本
- `search`：搜索相关知识片段
- `ask`：先检索再调用 LLM 生成回答
- `stats`：查看知识库统计信息
- `clear`：清空知识库

`RAGTool` 背后会创建 RAG pipeline。这个 pipeline 负责：

```text
文档转换 → 智能分块 → 向量化 → 存储 → 检索 → 问答
```

`rag_namespace` 用来做知识库隔离。比如不同用户、不同项目、不同文档集合，可以使用不同 namespace，避免检索结果混在一起。

因此可以把 RAG 系统也理解成三层：

```text
Agent
↓
RAGTool
↓
RAG Pipeline
↓
MarkItDown / Chunker / Embedder / Qdrant / LLM
```

## 16. 智能文档问答助手案例

8.4 节的智能文档问答助手，是把 `MemoryTool` 和 `RAGTool` 组合起来的完整案例。

核心类是 `PDFLearningAssistant`。它做了几件事：

- 初始化 `MemoryTool`，用 `user_id` 隔离不同用户的记忆
- 初始化 `RAGTool`，用 `rag_namespace` 隔离不同用户的知识库
- 维护 `session_id`，记录一次学习会话
- 维护 `stats`，统计加载文档数、提问次数、学习笔记数

加载 PDF 时：

```text
用户上传PDF
↓
RAGTool 处理PDF：MarkItDown转换、分块、向量化、入库
↓
MemoryTool 把“加载了某文档”记录到情景记忆
```

用户提问时：

```text
用户问题
↓
MemoryTool 先把当前问题写入工作记忆
↓
RAGTool 使用高级检索查找相关文档chunk
↓
LLM 基于检索结果生成回答
↓
MemoryTool 把这次问答记录到情景记忆
```

用户写笔记时：

```text
学习笔记
↓
MemoryTool 写入语义记忆
```

生成学习报告时：

```text
MemoryTool 获取记忆摘要
RAGTool 获取知识库统计
结合 stats 生成学习报告
```

这个案例的重点不是 Gradio 页面本身，而是它展示了一个完整应用如何把 RAG 和 Memory 串起来：

```text
RAG 负责“根据文档回答问题”
Memory 负责“记录用户学习过程和个性化信息”
```

## 17. 第八章最终总览

第 8 章可以用一句话概括：

```text
Memory 让 Agent 记住用户和历史，RAG 让 Agent 查到外部知识。
```

更完整地说：

```text
MemoryTool 解决“记住什么、如何找回、如何遗忘”
RAGTool 解决“文档如何入库、如何检索、如何增强回答”
Qdrant 负责向量相似检索
Neo4j 负责实体关系推理
SQLite 负责结构化持久化记录
Embedding 模型负责把文本变成向量
MarkItDown 负责把多格式文档统一转成 Markdown
```

本章最重要的工程思想是“分层封装”：

```text
上层 Agent 只调用工具
工具层提供统一接口
管理层负责调度
底层数据库和模型负责具体能力
```

这样做的好处是：Agent 不需要知道 Qdrant、Neo4j、SQLite、Embedding、MarkItDown 的细节，也能使用记忆和检索能力。
